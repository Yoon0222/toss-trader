# 아키텍처

```text
시세 수집 → 정규화 시세 → 스캐너 → 신호 엔진
뉴스·공시 → AI 분석 ────────────┘
신호 → 위험 검사 → 주문 실행 → Broker 인터페이스
                              ├ PaperBroker
                              └ TossBroker (Phase 1 차단)
체결·잔고 동기화 → 포지션 관리 → DB / 감사 이벤트
독립 스케줄러 → 거래일·세션 판단 → 위 작업 기동
FastAPI → 조회·운영 제어 → Next.js 한국어 대시보드
알림 outbox → Telegram
```

현재 코드는 app/config.py(설정), db.py(연결), models.py(영속 모델), broker.py(개발용 브로커·최소 위험 검사), main.py(상태 API)로 분리합니다. 스캐너·AI·스케줄러·대시보드는 설계만 포함하며 빈 구현을 완료 기능으로 표시하지 않습니다. Redis는 readiness에서 실제 ping을 수행하며 캐시·분산 잠금 용도는 후속 구현입니다.

## 영속 데이터

Account 1:N Order 1:N Fill, Account 1:N Position. 주문은 계좌와 client_order_id 조합 유일, 체결은 execution_id 유일입니다. 주문 상태에는 CREATED/ACCEPTED/PARTIALLY_FILLED/FILLED/CANCELED/REJECTED/UNKNOWN을 사용할 예정이며 상태 전이 검증은 후속 구현입니다. broker_order_id는 내부 중복키와 구분합니다. 현재 Position 수량은 공매도를 지원하지 않습니다. JSON 감사 정보에는 키·토큰·개인정보를 넣지 않아야 합니다.

운영 주문에서는 DB 트랜잭션 내 중복키 선점과 현금·수량 예약이 필요합니다. 네트워크 타임아웃은 UNKNOWN으로 기록하고 무조건 재주문하지 않습니다. 외부 주문 ID와 계좌를 조회해 재동기화합니다. Redis 잠금만으로 주문의 정확히 한 번 실행을 보장하지 않습니다. 외부 브로커와 DB 사이의 원자적 트랜잭션은 불가능하므로 대사 절차를 둡니다.

## 다음 단계

1. Phase 2: 공식 스키마 기반 읽기 전용 인증·시세·달력 어댑터. 공유 토큰 갱신 잠금, 그룹별 제한, WS 재연결·REST 대사, 실제 키가 필요한 연결 시험.
2. Phase 3: 급등주 점수·유동성 필터·시세 지연 검증.
3. Phase 4: 매수 A/B/C, 매도, 거래시간·전략·일일 손실·총 노출·중복·미체결을 포함한 전체 위험 관리.
4. Phase 5: 비용·체결 제약 포함 백테스트와 시간 분할·walk-forward 검증.
5. Phase 6: 영속 모의 계좌·미체결·부분체결·재시작 복구.
6. Phase 7~8: 인증된 한국어 UI·알림 outbox·거래일 기반 독립 스케줄러·운영 장애 시험.
7. Phase 9: 명시적 승인, 서버 설정, 계좌 권한, 복구·대사 검증 후 실전 전환 준비. 현재 코드에서는 설정만 바꿔도 실전 주문이 가능하지 않습니다.

Asia/Seoul 기준 스케줄은 향후 공식 거래 캘린더의 실제 세션을 기준으로 계산합니다. 평일만으로 거래일을 가정하지 않습니다. 서버의 restart 정책은 프로세스 재기동만 제공하며, 자동매매 스케줄 구현을 의미하지 않습니다.
